# 发布候选包校验

下一步不是直接操作生产环境，而是围绕发布安全构建一个可验证、可追溯、可复现的交付闭环。先生成不含 `Secret` 的候选发布包，再切换到 `staging-eu2` Kubernetes context，执行 `kubectl apply --server-side --dry-run=server -f dist/`，以此确保配置能够在真实 API 校验链路中实现无缝通过。

候选包包含三套具有阶段性意义的 manifest：副本数为 0 的停写清单、副本数为 1 的 canary 清单，以及副本数为 4 的正式清单。除此之外，还要包含数据库迁移 `Job`、27 个 `.sql` 迁移文件和覆盖全部文件的 `SHA256SUMS`。

需要特别强调的是，此步骤不会修改生产环境，也不会把任何 `Secret` 写入候选包。如果 server-side dry-run 报告字段不兼容或资源冲突，应立即停止，先修正候选包，再重新校验。通过这一机制，我们可以为后续生产发布奠定坚实基础。
