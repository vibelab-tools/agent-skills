# 发布候选包校验

下一步不是直接操作生产环境，而是建立一套围绕发布安全、可验证、可追溯且可复现的交付流程。首先生成不包含 `Secret` 的候选发布包，然后切换到 `staging-eu2` Kubernetes context（用于指定 Kubernetes 集群和命名空间等操作目标），执行 `kubectl apply --server-side --dry-run=server -f dist/`。该命令会通过真实 API 校验链路检查配置，但不会实际应用资源。

候选包必须包含三套具有不同发布阶段用途的 manifest（资源配置文件）：副本数为 0 的停写清单、副本数为 1 的 canary 清单，以及副本数为 4 的正式清单。此外，还必须包含数据库迁移 `Job`（用于执行一次性迁移任务）、27 个 `.sql` 迁移文件，以及覆盖全部文件的 `SHA256SUMS` 校验和清单。

需要特别注意的是，这一步不会修改生产环境，也不会将任何 `Secret` 写入候选包。如果 server-side dry-run 报告字段不兼容或资源冲突，应立即停止，先修正候选包，再重新执行校验。通过这套流程，可以为后续生产发布提供可靠的验证依据。
