# OAuth 2.0 Explained for Junior Developers

OAuth 2.0 is a protocol for delegated authorization. If you have clicked "Sign in with Google," you have probably used OAuth.

OAuth handles authorization, not authentication. Authentication verifies who you are. Authorization determines what you can access. With OAuth 2.0, a third-party application can access resources such as your email address or calendar without receiving your password.

OAuth uses four roles:

- The resource owner is the user.
- The client is the application requesting access.
- The authorization server issues tokens.
- The resource server stores the protected data.

The most common flow is the Authorization Code flow. First, the client redirects the user to the authorization server. The user grants access there, and the authorization server sends an authorization code to the client's redirect URI. The client then exchanges that code and its client secret for an access token. It uses the access token to request data from the resource server.

Access tokens are usually short-lived and often expire after about an hour. A refresh token lets the client request a new access token without asking the user to grant access again.

Single-page applications use the PKCE extension, which stands for Proof Key for Code Exchange. PKCE adds protection while avoiding the need to store a client secret in the browser.

These concepts cover the basic OAuth 2.0 flow and provide a starting point for working with APIs that use it.
